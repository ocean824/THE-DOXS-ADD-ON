# DOX-v1 — Connect the existing Dox website to D.O.X Workspace

Modify the EXISTING www.thedoxs.com application to send owner-authorized referrals to a separate D.O.X Workspace CRM over HTTPS. Do not rebuild the CRM, copy its database or assume shared sessions. Get the actual CRM BASE_URL and current OpenAPI schema from the owner. The CRM is the single source of truth for transactions, contacts, reviews, tasks, documents and message threads.

CRM permissions: OWNER full access; TEAM_MEMBER assigned records only, no contact deletion/user management/AI logs; CLIENT view-only on linked transactions, client-visible documents and their threads. The Dox integration is NOT any of these human roles; it has only contacts:ingest. The CRM validates permissions on every endpoint.

Have the owner create a Dox service key in CRM > Connections, then store it in Dox's BACKEND secret store as DOX_CRM_SERVICE_KEY. Store the CRM HTTPS base URL as DOX_CRM_BASE_URL. Never send either integration credentials or CRM LLM secrets to the browser, model prompts, email, logs or public URLs. No CORS access or embedded cross-site cookie session is needed: this is server-to-server.

Implement a Dox owner-only action/screen labelled Send referral to CRM. Display the referral's contact fields and require owner confirmation; keep a server-side delivery receipt. Only send contacts who are legitimately authorized for this workflow. The browser sends a Dox record ID, never arbitrary URLs or markup. The Dox backend loads and authorizes that record, maps it, and POSTs {BASE_URL}/api/integrations/dox/contacts with Authorization: Bearer <service key> and JSON {name:string (2-100),email:email,phone:string,company:string,type:"buyer"|"seller"|"partner",tags:string[],notes:string,assigned_ids:[]}. The CRM ignores external assignment grants and assigns imported contacts to its active owner. The response is the canonical contact {id,name,email,phone,company,type,tags,notes,assigned_ids,created_by,created_at}. Contacts with the same source service and email deduplicate. Reissuing the service credential creates a new source identity; keep canonical CRM IDs in receipts and avoid automatic resubmission after credential rotation.

The Dox backend may store only the reference to its own referral and the returned CRM contact ID, delivery status, and timestamp; no competing transaction database. Return errors honestly. 401 means invalid/revoked key; 403 insufficient scope; 422 invalid payload; 503 unavailable. Backoff for transport errors, never claim successful delivery without a successful response. There is no reverse-sync webhook in v1: do not invent an endpoint or claim transaction synchronization exists.

For an optional Open CRM link, direct users to the separate CRM's login page; do not share Dox passwords/JWTs. Future SSO requires a separate reviewed integration. Human desktop/phone clients authenticate directly using POST /api/auth/login; browser cookies are Secure HttpOnly, desktop bearer tokens go in OS secure storage; refresh/logout via /api/auth/refresh and /api/auth/logout.

Related entity model: transactions link buyer_id/seller_id contacts and assigned_ids/client_ids users; tasks/documents/reviews belong to transaction_id; review_comments belong to review_id and transaction_id; threads attach transaction_id/contact_id and participant_ids; messages belong to thread_id; AI logs are owner-only. No service-key endpoint can retrieve these through the Dox scope. LLM requests go only through /api/ai/chat; no LLM keys in Dox or Traycer.

Deliver the Dox backend action, owner-only UI, a setup checklist and tests proving non-owner denial, no frontend secret disclosure, successful contact ingestion and retry deduplication. This is DOX-v1, compatible with HERMES-v1 and TRAYCER-v1.
