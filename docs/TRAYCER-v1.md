# TRAYCER-v1 — Windows 11 client for the existing D.O.X Workspace API

Build a Windows 11 desktop client using Electron or Tauri, not another CRM backend. Read BASE_URL from staging/production settings controlled by the owner; HTTPS only, no hardcoded live hostname. Obtain the actual request/response contracts from authenticated GET {BASE_URL}/api/openapi.json. The website API is the only authority for users, permissions, records, approvals, messages and AI usage.

Use native-feeling Windows surfaces, system light/dark preference, tray icon, toast notifications, offline indicator, retry controls, app icon, signed auto-update design and .exe/MSIX installer. Match the D.O.X identity with restrained typography and gold highlights where appropriate. Do not produce an unsigned public auto-update endpoint as if it were safe.

Auth screen: POST /api/auth/login {email,password,client:"desktop"}. Response {user:{id,name,email,role,active,notification_preferences,created_at},access_token,refresh_token,token_type:"bearer",expires_in:900}. Secure tokens using Windows Credential Manager/DPAPI via an audited native binding; never plaintext files, localStorage or renderer globals. Main process owns tokens and network operations; contextIsolation on, nodeIntegration off, narrow IPC allow-list, navigation restricted. Attach Authorization: Bearer <access_token>. On expiration, POST /api/auth/refresh {refresh_token}; atomically replace BOTH tokens because refresh rotates. On failed refresh/401 clear credentials and return to login. POST /api/auth/logout revokes the session; clear secure storage regardless of network failure, and do not call a local logout a guaranteed server revocation if offline.

Roles: OWNER full CRM/user/policy/log access; TEAM_MEMBER only assigned contacts, transactions and participant threads, no contact deletion, user management or AI logs; CLIENT read-only linked transactions, client-visible documents and own message threads. Role UI must reflect server user data, never implement a client-side role switch or rely on UI gates for security.

Screens and endpoints:
1. Dashboard: GET /api/transactions, /api/tasks (staff only), /api/activity, /api/notifications. Due dates use YYYY-MM-DD. Highlight overdue and due-in-24-hour tasks. GET /api/directory resolves names. CLIENT skips staff-only routes.
2. Transactions: GET /api/pipeline-stages and /api/transactions; filter/search locally within the authorized result set. Detail GET /api/transactions/{id}, /api/transactions/{id}/tasks (staff), /api/transactions/{id}/documents. PATCH /api/tasks/{id} {completed,due_date?,assignee_id?} for staff. GET /api/documents/{id}/download returns an authenticated attachment; save via OS dialog with safe filename handling, never automatic execution. POST multipart /api/transactions/{id}/documents has file, category and visibility internal|client; max20MB, PDF/DOCX/PNG/JPG/TXT. Documents cannot be uploaded by CLIENT.
3. Reviews: staff GET /api/reviews; detail GET /api/reviews/{id}, /api/reviews/{id}/comments. POST /api/transactions/{id}/reviews {note} submits; POST /api/reviews/{id}/comments {body}; OWNER POST /api/reviews/{id}/decision {decision:"approved"|"rejected"|"revision_requested",note}. Rejection/revision notes required. Submitter cannot approve their own review. Show checklist completeness and missing required document categories alongside comments. Do not calculate an approval permission locally.
4. Inbox: GET /api/threads (unread counts), GET /api/threads/{id}/messages, POST /api/threads/{id}/read. Staff replies POST /api/threads/{id}/messages {body,mention_ids:[]}; mention IDs must be participants. CLIENT can mark read but cannot send. Message response includes read_by. POST /api/threads {title,transaction_id?,contact_id?,participant_ids} requires at least one attached record and authorized participants.
5. Assistant: POST /api/ai/chat {template:"draft_email"|"summarize"|"closing_recap"|"missing_items",transaction_id,prompt:"optional context"}. HTTP SSE stream contains data JSON {type:"delta",text}, then {type:"done",log_id} or {type:"error",message}. Parse chunks across line boundaries. GPT-5.2 is server-side only. GET /api/ai/usage returns {used,limit,model}; limit null is owner unlimited. CLIENT cannot use missing_items. Do not give this panel filesystem/shell tools. No AI key, service key, hidden user data or system prompt in the app.
6. Notifications: authenticated GET /api/events SSE emits ready, change {timestamp}, expired. On change invalidate authorized views and refetch /api/notifications. SSE must carry bearer authorization from the main process. On expired refresh credentials/reconnect. Fallback poll /api/notifications every60seconds while signed in; deduplicate IDs and show Windows toasts only for enabled categories. PATCH /api/notifications/{id}/read marks stored notifications; computed IDs prefixed task- reflect open due tasks and are cleared by task state, not this endpoint. PATCH /api/notification-preferences {messages,tasks,mentions}.

Data model: users {id,name,email,role,active}; contacts {id,name,type,email,phone,company,tags,notes,assigned_ids}; pipeline stages {id,name,color,position}; transactions {id,address,city,state,zip,value,property_type,stage_id,buyer_id,seller_id,agent,contract_date,contingency_date,closing_date,assigned_ids,client_ids,image_url,review_status,required_documents,created_by,created_at,sample}; tasks {id,transaction_id,title,due_date,assignee_id,completed}; documents {id,transaction_id,filename,content_type,size,category,visibility,uploaded_by}; reviews {id,transaction_id,submitted_by,status,note,decided_by,decided_at}; review_comments {review_id,transaction_id,author_id,author_name,body}; threads {id,title,transaction_id,contact_id,participant_ids,last_message,last_message_at,unread}; messages {id,thread_id,sender_id,sender_name,body,mention_ids,read_by,created_at}; owner-only ai_usage_logs track prompt,response,status,user,template,transaction. IDs are UUID strings; created_at timestamps are UTC ISO8601.

Handle 403 as permission denial, 404 as unavailable record without probing, 409 as conflict requiring refresh, 422 field validation, 429 rate-limit message, 503 temporary integration failure. No silent offline mutations: keep only minimal encrypted read cache and purge it on logout/user switch. Don't cache documents by default. Never send an approval without an explicit click.

Hermes uses a separate scoped server-to-server bridge defined by HERMES-v1; Traycer never holds its service key. Traycer observes approved decisions via the same CRM APIs and event feed. All phone confirmation, autonomous value caps and completeness rules are enforced on the CRM server, not in Traycer.

Deliver source, Windows build commands, secure-token setup, installer instructions, signing/auto-update prerequisites, API base URL settings documentation, permissions matrix tests, offline/reconnect tests, and screenshots. Do not claim a Windows installer or phone service is shipped until actually built and tested on Windows/mobile. Compatible with DOX-v1 and HERMES-v1.
## Knowledge vault, calendar and client uploads (added in this revision)

- Knowledge vault (all roles): GET /api/knowledge/access returns {shared_items,project_items,grants,items[]} filtered server-side to what the signed-in user may use; GET /api/knowledge/items/{id} returns extracted text. Do not cache vault text across users. Owner-only: POST /api/knowledge/sync {items:[{path,content,encoding:"text"|"base64"}],scope,transaction_id,project_type,tags,deleted_paths} (batches of ≤100, ≤25 MB per file; .md .txt .csv .json .yaml .docx .xlsx .pptx .pdf), PATCH/DELETE /api/knowledge/items/{id}, GET/POST/DELETE /api/knowledge/grants. A desktop "Sync folder" action should mirror the reference CLI (GET /api/integrations/cli, owner-only) by walking a local Obsidian/Office folder and sending unchanged files too (server hashes and skips them). Use --prune semantics only when the user explicitly asks to remove missing files.
- AI knowledge template: POST /api/ai/chat {template:"knowledge",prompt,transaction_id?}; the done frame now includes sources:[{id,title,path}]. Render sources as chips. Other templates still require transaction_id.
- Calendar: GET /api/meetings (participant-scoped; owner sees all); POST /api/meetings {transaction_id,title,starts_at:"YYYY-MM-DDTHH:MM",duration_minutes,location,notes,participant_ids}; PATCH /api/meetings/{id} (organizer/owner; rescheduling resets responses to pending; status:"cancelled" cancels); POST /api/meetings/{id}/respond {response:"accepted"|"declined"}. Participants must be owners or people assigned/linked to the transaction. Combine with transaction contract/contingency/closing dates for month and week views. Meeting notifications link to /calendar?meeting={id}.
- Client uploads: CLIENT may POST /api/transactions/{id}/documents for linked transactions; visibility is forced to "client" and the document carries client_submitted:true and uploaded_by_name. Assigned staff and owners receive a notification. Show a "Client submitted" badge.
